## Three Properties That Fail Independently

**Pair: an encrypted-but-unauthenticated channel.** It is like a page mapping with the read bit cleared and the write bit still set, and it is like a git repository you cannot clone but everyone can force-push to. The shared structure is that read permission and write permission are separate bits in the same ACL, and clearing one says nothing about the other. Your intuition already accepts this in both systems: nobody argues that a write-protected file is therefore unreadable, or that a private repo is therefore append-only. Encryption clears the read bit. It never touched the write bit.

Where this breaks: in both analogies there is a referee. The MMU faults on the illegal write, the git server rejects the push. There is no referee on a wire. The receiver of a tampered CTR-mode ciphertext does not get a fault, an error, or a rejected push; it gets plaintext that decrypts cleanly and reads as legitimate. The analogy gives you the independence of the two permissions and then overstates the enforcement, which is exactly the part crypto has to supply separately.

**Pair: CRC32 as an integrity mechanism.** A CRC is like an HTTP `ETag` used for optimistic concurrency, and it is like a Kubernetes `resourceVersion` on a compare-and-swap update. The shared structure is a short token that detects an unintended change by a cooperating participant: two clients racing on the same object, a NIC flipping a bit, a disk returning a stale sector. All three are collision-detection for accidents.

Where this breaks: `ETag` and `resourceVersion` are minted by the server and validated by the server, so a client cannot fabricate one that certifies a change the server did not authorize. A CRC travels with the data and is computable by anyone, so an attacker who edits the message recomputes the token. Worse, and this is where every SE analogy runs out, CRC32 is linear over XOR: $\mathrm{CRC}(M \oplus d) = \mathrm{CRC}(M) \oplus \mathrm{CRC}(d)$. The attacker does not even need to see $M$ to fix up the checksum through the encryption. No optimistic-concurrency token you have used has that algebraic property, which is why the analogy will not warn you about it.

**Pair: integrity versus authenticity.** Integrity is like verifying a downloaded artifact against a `SHA256SUMS` file, and authenticity is like verifying the detached GPG signature on that `SHA256SUMS` file. The shared structure is that both answer a question about provenance of bytes; the first asks "are these the bytes that were published," the second asks "who published them." In practice one keyed primitive answers both, because a valid MAC tag proves the tag was produced by a keyholder over exactly these bytes.

Where this breaks: the artifact analogy makes the two look like layers you can stack in either order and at any time, since checksum files and signature files are separate artifacts on a mirror. In a live protocol the ordering of encryption and authentication is load-bearing and the wrong order is exploitable; unit 3 spends a section on it. Treat the analogy as a definition of terms, not as a composition rule.

## Threat Models: What the Attacker Gets to Do

**Pair: Kerckhoffs's principle.** It is like assuming your mobile app binary will be decompiled, and it is like committing your Terraform to a public repo while the credentials live in a vault injected at runtime. The shared structure is a hard line between what ships and what is provisioned. Everything that ships is public by assumption: source, config, state machine, constants. Only the runtime-injected material is secret, and it is the only thing you get to rotate.

Where this breaks: in ops, obscurity has real, if small, value. An unlisted admin endpoint genuinely reduces drive-by scanning volume, and nobody calls that a design flaw. Crypto refuses to count that value at all, because the failure modes differ in kind rather than degree: a leaked key is a rotation, a leaked algorithm you were depending on is a redesign of every deployment. The analogy correctly identifies the boundary and understates how absolute crypto is about it.

**Pair: passive versus active attackers.** A passive attacker is like `tcpdump` on a SPAN port or a read replica with no write path back; an active attacker is like a service-mesh sidecar or a transparent TLS-terminating proxy sitting in the request path. The shared structure is the difference between a tap and a man-in-the-path element. The tap can only correlate what it sees. The path element can drop, delay, reorder, duplicate, and rewrite, and every one of those verbs is a separate attack primitive.

Where this breaks: your sidecar is trusted and configured by you, so you think of it as infrastructure rather than as an adversary with rewrite privileges. Flip the trust and the capability list is identical. Also, the analogy suggests the two categories are far apart operationally. They are not: a passive tap plus one injected packet that wins a race is an active attacker, and off-path spoofing gets you there without any privileged position.

**Pair: the CPA oracle.** It is like a public `/preview` endpoint that renders your input using the production signing key, and it is like a logging pipeline where the attacker-supplied `User-Agent` lands in the same encrypted record as a session cookie. The shared structure is attacker-chosen bytes being processed under the target key, at attacker-chosen volume, with output the attacker can observe. Once you see it this way, chosen-plaintext access stops looking like an academic concession and starts looking like the default deployment.

Where this breaks: those endpoints have rate limits, and rate limits make you think the oracle is bounded. The IND-CPA definition grants unbounded queries because the interesting attacks need very few. A distinguisher that wins on the second query does not care about your rate limiter.

**Pair: the CCA oracle.** It is like an API that returns `400` for malformed JSON and `500` for a downstream failure, and it is like a cache whose hit and miss paths have different latency. The shared structure is that the failure mode is an output channel. You added the distinction for debuggability or performance; the attacker reads it as one bit per query, and one bit per query with unbounded queries is a decryption oracle.

Where this breaks: in normal API design, distinguishable errors are correct and desirable, and you tune latency to be as different as possible between fast and slow paths. Decryption inverts both preferences. Every observable difference on the failure path, including timing, log volume, and connection-reset behaviour, is leakage, which is why unit 3's constant-time verification code looks so unnatural.

**Pair: the IND-CPA game and negligible advantage.** The game is like an A/B test where the null hypothesis is "the ciphertext carries no signal about which branch ran," and it is like a binary classifier scored against a coin flip, where advantage is the lift above 0.5 AUC. The shared structure is measuring how far above chance a decision procedure gets, on a fixed effect, with as many samples as it wants.

Where this breaks: an A/B test quantifies over one pre-registered test statistic that you wrote down; IND-CPA quantifies over every efficient adversary, including the ones nobody has written yet, which is why the claim is a universally quantified bound rather than a measurement. And the asymptotics mislead: negligible is like the error term you drop in big-O reasoning, but real deployments ship one fixed key size, so the asymptotic statement has to be cashed out concretely. "Negligible" means $2^{-128}$ on the hardware that exists, not "tends to zero."

## XOR and the One-Time Pad

**Pair: XOR as its own inverse.** Encryption by keystream XOR is like applying a binary delta, and it is like a database migration whose `up` and `down` are the same script. The shared structure is an involution: run it twice on the same argument and you are back where you started, so encrypt and decrypt are one code path with no branch, no mode flag, and no state. This is why stream-cipher implementations look suspiciously short.

Where this breaks: a delta and a reversible migration both carry structure that identifies what changed, and both are meaningful to inspect. The keystream carries none; it is uniform noise with no schema, which is exactly what makes the result reveal nothing and also exactly what makes tampering undetectable. An involution has no notion of a valid target state to check against.

**Pair: perfect secrecy.** The one-time pad is like a lookup table with a distinct, independently chosen row for every possible input, and it is like a `UUIDv4` handed out per record with no derivation from record content. The shared structure is that the output is a fresh uniform sample carrying zero mutual information with the input: knowing the output narrows the input by nothing, because every input maps to that output under exactly one key, and all keys are equally likely.

Where this breaks: both analogies quietly require storing something as large as the data itself, and that is the entire cost of the pad. The table has a row per input; the UUID map has an entry per record. Which leads directly to the second pair.

**Pair: the key distribution problem.** Shipping one-time-pad key material is like solving a cache-consistency problem by rsyncing the whole database, and it is like fixing a slow diff by mailing the full checkout on a drive. The shared structure is that the "solution" has the same cost profile as the original problem: you need a secure channel for $n$ bytes of key in order to protect $n$ bytes of message, so you already had the secure channel.

Where this breaks: sneakernet actually is a rational answer when bandwidth is the constraint and latency is not, and pads genuinely were used this way for diplomatic traffic. The analogy fails on freshness rather than volume: a stale rsync is merely stale, while a reused pad is catastrophic, which is the next pair.

**Pair: two-time pad.** Reusing a pad is like diffing two branches that share a base commit, where the shared base cancels out entirely and you are left with the difference between the two working trees, and it is like a deterministically encrypted database column where equality joins still work on the ciphertext. The shared structure is that an identical secret applied to both operands cancels under the combining operation, leaving a pure relation between the two plaintexts with no key material in it. $c_1 \oplus c_2 = m_1 \oplus m_2$ is a diff with the base removed.

Where this breaks: `git diff` needs both revisions in hand and produces a human-readable patch; the attacker gets only the XOR and has to recover the operands from it, which takes guessable structure in one message (a fixed header, a JSON key name, an English word) and iteration. That is crib-dragging, and it is why "the plaintexts are compressed/binary/proprietary" is not a defence. It slows the attack down, it does not restore the property.

## Modular Arithmetic and Groups, Refreshed

**Pair: reduction mod $n$.** It is like `uint8` wraparound, and it is like a ring buffer's write index advancing with `idx = (idx + 1) % cap`. The shared structure is a finite state space wired into a cycle, where the successor of the last element is the first and the carry is discarded rather than promoted. You already reason fluently about this; $\mathbb{Z}_n$ is that, promoted from an implementation nuisance to the object of study.

Where this breaks: in two places, both of which bite. First, sign. C, Java, and Go define `%` to follow the sign of the dividend, so `-3 % 7` is `-3` while $-3 \bmod 7 = 4$; every ring-buffer bug you have written from a negative index is the same bug. Second, invertibility. Arithmetic mod $256$ is a ring, not a group under multiplication: only odd values have inverses. Mod a prime $p$, every nonzero value does, and that is precisely the property units 4 and 5 are built on. `uint8` will not teach it to you because $256$ is not prime.

**Pair: reducing early.** The identity $(a \cdot b) \bmod n = ((a \bmod n) \cdot (b \bmod n)) \bmod n$ is like a map-reduce combiner doing partial aggregation before the shuffle, and it is like folding a monoid in any association order. The shared structure is that the operation commutes with the projection, so you can push the reduction down toward the leaves and keep every intermediate bounded. This is the only reason a 2048-bit modular exponentiation fits in memory.

Where this breaks: the homomorphism covers addition and multiplication and nothing else. Comparison does not survive it, because $\mathbb{Z}_n$ has no order you can trust: $17 \equiv 5 \pmod{12}$ and asking which is larger is a category error. Neither does exponentiation, because exponents live mod $p-1$ while bases live mod $p$. A combiner that reduces the exponent by the wrong modulus is a real and common bug, and no aggregation intuition will flag it.

**Pair: repeated squaring.** It is like binary lifting for lowest-common-ancestor queries, where you precompute jumps of $2^0, 2^1, 2^2, \ldots$ and select the ones the bits of the distance turn on, and it is like fast doubling for Fibonacci. The shared structure is that the binary expansion of the exponent selects a subset of precomputed doubling steps, turning $O(e)$ into $O(\log e)$. $3^{13}$ with $13 = 1101_2$ is four squarings and two selections.

Where this breaks: hard, and this is the most important breakdown point in the section. Binary lifting branches on the bits of a public query. Modular exponentiation in a signature or a key exchange branches on the bits of a private exponent, and a branch that depends on a secret is a timing and power side channel that leaks that secret one bit at a time. Production implementations do not use the textbook square-and-multiply above; they use Montgomery ladders or fixed-window forms that perform the same operation sequence regardless of the exponent bits. The algorithm you learn here is correct and the code you write from it is not shippable.

**Pair: a group.** It is like an interface with four laws attached, in the sense of a `Monoid` extended with `invert`, and it is like the command pattern where every command is required to implement `undo()`. The shared structure maps one to one: closure is the operation being total and type-preserving, associativity is being allowed to batch or reassociate, identity is the no-op command, and inverses are undo. The group order $|G|$ is the size of the state space.

Where this breaks: `undo()` implies you know how many steps you took, and the entire security of unit 4 rests on the opposite. In $\mathbb{Z}_p^*$, undoing a single multiplication is cheap, but recovering "how many times was $g$ applied" from the result is believed infeasible. The command-pattern intuition also imports commutativity you should not assume in general; the specific groups here happen to be abelian, and elliptic curves are written additively ($xG$ rather than $g^x$) purely as typographical convention.

**Pair: cyclic groups and generators.** A generator is like the multiplier in a full-period linear congruential generator, which visits every state in its space exactly once before returning to the seed, and it is like a hash ring walked by a single fixed stride that touches every slot. The shared structure is that iterating one step from one starting point enumerates the whole set, and the period equals the size of the set. For $\mathbb{Z}_7^*$ with $g = 3$, the powers $3, 2, 6, 4, 5, 1$ hit all six elements and land on the identity exactly at the order, which is Fermat's little theorem showing up as a cycle length.

Where this breaks: an LCG is trivially invertible. Given a state you multiply by the modular inverse of the multiplier and walk backwards, which is why nobody uses one for anything security-relevant. The crypto group has the same enumeration property and the opposite inversion property: stepping forward is $O(\log x)$, counting steps is not known to be feasible. If the LCG analogy is doing any work for you, it is doing it on the structure of the cycle only, never on the difficulty.

**Pair: the discrete logarithm problem.** It is like a content-addressed hash, where you compute the digest from the content cheaply and cannot reconstruct the content from the digest, and it is like a git commit id. The shared structure is a cheap forward direction and an inverse that nobody knows how to compute in feasible time.

Where this breaks: a hash is lossy and non-injective, and its irreversibility is partly information-theoretic since many inputs collapse to one digest. Modular exponentiation over a cyclic group is a bijection. The answer is uniquely determined and fully present in the output; it is hidden by cost alone. That difference has two consequences. It is why discrete log has exploitable algebraic structure that hashes lack, giving both the index-calculus and number-field-sieve attacks that make finite-field discrete log subexponential rather than exponential, and giving Diffie-Hellman its commuting property in the first place. Same asymmetry, entirely different internals, and unit 4's key-size table is a direct consequence.

## Keyspace, Bits of Security, and the Exponent

**Pair: key length as an exponent.** Adding a key bit is like adding a level to a perfect binary tree, and it is like incrementing $n$ in an $O(2^n)$ algorithm you would refuse to ship. The shared structure is that the parameter sits in the exponent, so the increment is multiplicative in the work: one more level doubles the leaves, one more bit doubles the attacker's search. You already have correct instincts here, from the other side of the table: you know that an exact-cover solver going from $n = 40$ to $n = 48$ is a 256x regression, not a 20 percent one. A 128-bit to 256-bit key is the same arithmetic pointed at the adversary, and the ratio is $2^{128}$, not $2$.

Where this breaks: for your own algorithms you attack the exponent and are usually rewarded, which trains an optimism that does not belong here. The attacker's exponent is set by the best known algorithm, not by your key length, and it only ever moves down. Which is the next pair.

**Pair: bits of security.** It is like an availability estimate taken as the minimum over all failure paths rather than the average, and it is like a security review rating being set by the cheapest exploit found rather than by the count of controls in place. The shared structure is a bound quantified over adversary strategies: the number is a minimum over attacks, so every newly discovered attack can only lower it, never raise it. A 128-bit key with a $2^{40}$ cryptanalytic shortcut gives 40 bits, and the key length was never the measurement.

Where this breaks: an availability number is computed from telemetry of events that happened. Bits of security is a claim about attacks that have not been published, so it is an estimate with a downward-only ratchet and no measurement behind it. That asymmetry is the whole argument for margin, and it is why the 256-bit key exists despite 128 already exceeding the age of the universe.

**Pair: entropy versus key width.** The distinction is like a `UUIDv4` occupying 128 bits of column width while carrying 122 bits of randomness, and it is like an `int64` primary key holding an autoincrement value: the field is 64 bits wide and the cardinality is your row count. The shared structure is that container width is an upper bound on, not a measure of, the number of distinct values an adversary must enumerate. An AES key derived from an 8-character password is 128 bits wide with a $2^{52.6}$ search space, and the buffer size tells you nothing.

Where this breaks: for database ids, the number you care about is the collision threshold, which by the birthday bound sits at roughly the square root of the space. For keys, the number you care about is exhaustive search, which is the full space. Same bit count, different threshold, and unit 2 shows a single hash function exhibiting both bounds for different properties at once. Do not carry one intuition into the other.

**Pair: key derivation functions.** PBKDF2, scrypt, and Argon2 are like adding a fixed cost per attempt to a login rate limiter, and they are like requiring proof-of-work on an expensive endpoint. The shared structure is multiplying the adversary's per-guess cost by a constant so that a small search space becomes annoying to enumerate.

Where this breaks: in two opposite directions, and both are worth internalizing. In favour of the KDF, a rate limiter lives on your server and evaporates the moment the attacker dumps the database and goes offline, whereas the KDF cost is baked into the stored value and travels with it. Against the KDF, a constant factor cannot repair a missing exponent. Twenty bits of added work factor is twenty bits, and it is bounded above by what your legitimate users will tolerate in login latency, since they pay it too. A 52-bit password with a 20-bit KDF is a 72-bit secret, which is still under the 128-bit floor.

**Pair: multi-target attacks and Grover.** Multi-target search is like credential stuffing against a whole user table rather than one account, where the attacker wins on any match and the cost divides by the number of targets. Grover's algorithm is like replacing a linear scan with a $\sqrt{N}$ index probe, taking $2^n$ to about $2^{n/2}$. The shared structure across both is that the exponent, not the constant, is what moves: multi-target subtracts $\log_2 N$ from it, Grover halves it, and only changes at that level matter.

Where this breaks: the credential-stuffing analogy stops applying once keys are salted or context-bound, since per-session keys derived with distinct context are not a shared target pool, which is exactly what unit 6's key schedule is arranging. And the index analogy oversells Grover: a $\sqrt{N}$ index probe shards cleanly across machines, while Grover's $2^{64}$ steps are inherently sequential and parallelizing across $P$ quantum machines buys only $\sqrt{P}$. The speedup is real, it is not a linear-scale resource you can throw a data centre at, and "AES-256 for post-quantum margin" is a hedge rather than an emergency.
